# Native import recovery: upgrade and rollback boundary

## Storage and mixed-version admission

- SQLite migration adds nullable `recovery_task_id` and a BEFORE INSERT trigger in one IMMEDIATE transaction. The trigger rejects the old runtime's ordinary call INSERT while a recovery call exists for the same workspace. Old processes can still read the journal; the trigger is not an OS-wide filesystem lock. Do not remove it during application rollback. An unresolved import remains protected by the native and durable-index fences.
- Native ledger reader accepts schemas 1, 2 and 3. Ordinary legacy records remain V2 until V3 validation or legacy boot evidence is written. V3 stays V3 thereafter. V3 fields in a V1/V2 envelope are rejected. The aborted import tombstone is version 2; previously prepared/published transactions remain version 1.
- Native V3 is forward-only: the old strict reader cannot load it. This is intentional fail-closed behavior, not a supported downgrade. A rollback of an app slot must retain the compatible stable native service and shared admission trigger; the managed updater's slot rollback is distinct from replacing the stable service binary.
- Do not install an older native service or restore a pre-recovery ledger/profile snapshot over current authority state. That can lose reservations or resurrect attempts. Recover service availability using a vetted forward-compatible service retaining current ledger/tombstones. A binary-only old-service rollback is blocked by policy, not proven to be prevented by a historical installer. Installer-level downgrade refusal, actual signed-package/SCM and app-slot rollback compatibility require separate release qualification.

## Legacy prepared import

For a terminal verified, still-held, exact-owner import with explicit publication-not-committed evidence but missing validation evidence:

1. Request exact terminal recovery through `git_clone_cancel` with `recoverTerminal: true` under chat confirmation and trusted one-shot host approval. No unrelated operation or live cancellation is permitted in this route.
2. The service reads its kernel Boot ID, persists a witness in the protected ledger, and returns `SERVICE_IMPORT_LEGACY_NEW_BOOT_REQUIRED`. Both reservations stay held. Repeated requests or service restart on the same boot cannot authorize release.
3. A separately authorized full OS reboot is required after the witness. No caller timestamp or caller-provided boot identifier is accepted.
4. Retry with fresh host approval. The native service requires a distinct kernel Boot ID, an absent exact attempt-named Job, verified terminal metadata, explicit publication fence, exact transaction/request/owner and pinned filesystem identities. Only then does it persist the verified boot evidence and aborted tombstone before releasing the native hold. The runtime must independently reconcile its own marker.
5. An old missing launch executable may be recovered only as a candidate from the exact durable worker spec and matching task metadata; the original request digest is recomputed. It is never executed. Missing/mismatched proof, absent transaction, unknown/active worker, publication ambiguity, replaced stage/parent, or modern pending validation remains blocked.

The observed boot and verified boot are separate durable evidence, not an invented `ImportValidationPending=false`. A new boot is not proof of publication state. The recovery does not delete/rename the stage or destination, restore the repository, or grant a writer lease.

## Installer transition (R5)

The candidate NSIS setup runs the embedded candidate helper's read-only `service-install-preflight` in customInit before the old uninstaller and application extraction. For an existing protected service the operator must independently quiesce it (disabled and SCM stopped with PID zero) and run setup elevated. Setup never requests that stop automatically. The native helper rechecks service state and protected storage before registration/removal. Missing or untrusted authority, nonterminal attempts, duplicate identities, missing/orphan import records, and incompatible schema fail closed. An exact V2 TerminalVerified/Prepared exclusive import with explicit nonpublication fence and absent named Job may be carried forward without release by a candidate upgrade from a predecessor; the current uninstaller refuses held authority. Ordinary cancellation cannot request a legacy boot witness or finish a held legacy abort. The explicit recovery route adds the native request selector, but this is not a cryptographic host approval token; native SID and evidence checks remain mandatory.

V3 blocks ordinary native uninstall/replacement even after recovery. A supported forward-compatible repair/update mechanism is still required; do not use a historical installer or restore an earlier authority snapshot. A historic installer cannot be retroactively patched; refusal of the current uninstaller helps on the normal uninstall path but cannot guarantee an old installer will honor launch errors, or protect against a privileged administrator directly replacing service files. Quiescence is an observation, not a cross-installer maintenance lock. No upgrade is supported for a registered service with missing ledger or an unresolved nonterminal record. Managed application-slot rollback/profile relocation remains unqualified (native endpoint pins may require matching packages). Do not use these paths as a workaround.

## Forward replacement (R6; candidate only, not release-qualified)

The explicit administrator maintenance lane is separate from NSIS and managed slot updates: a protected, independently authenticated candidate helper supports `service-replace-preflight <current-helper-sha256> <candidate-helper-sha256>` (read-only) and `service-replace <current-helper-sha256> <candidate-helper-sha256>` (mutating, requires separate authorization). These are not instructions to run either command on a live host. The approved candidate and existing image hashes must come from independent package evidence, not merely the candidate's own manifest. The candidate must already be staged under a protected Program Files package tree, with matching manifest and native pin; no arbitrary image path input, ACL repair, app deployment, or removal of the previous tree is performed by this lane. Existing managed enrollment, private update authority, slot-image paths, and nested old/new roots are refused. The current registration must already be independently disabled/stopped with PID zero and LocalSystem account. No automatic service stop or task cancellation.

Forward-only policy reads V1/V2/V3 without rewriting them; unsupported schema, active/unknown attempts, pending validation, unresolved publication, missing import records, conflicting holds, and corrupt/mismatched tombstones are refused. An exact eligible held import (including V3 boot witness or a durable abort tombstone before hold release) remains held. A released V3 abort tombstone remains unchanged. Ordinary NSIS and uninstall still refuse V3. New uninstaller also refuses deletion when the registered image differs from its own image. This cannot retroactively harden an older installed helper or historical setup.

Sequence: verify and pin protected packages, validate current SCM/store, register candidate while disabled, recheck configuration and store, select demand-start and verify stopped candidate, start, require authenticated native RPC and stable running PID, then enable auto-start and recheck. After any error, preserve observed registration and authority; never stop a possibly admitted writer, delete service, reset data, or automatically revert the old image. A failed activation needs manual investigation, not automatic retries. Concurrent privileged maintenance remains outside this lane; do not run installers concurrently. The command verifies caller-supplied image pins and compatible ledger; it does not itself establish signed-release provenance, version monotonicity, or full application package acceptance. The old desktop runtime may refuse the new helper hash until the matching desktop runtime is deployed.

Acceptance on a disposable Windows VM/Sandbox or hosted test runner only: start with a verified predecessor and matching candidate packages; prove ordinary NSIS downgrade/uninstall refuses V3 without changing SCM/image/store; exercise read-only preflight with incorrect hash, running service, mismatched account, unknown/pending attempt and managed authority; verify eligible V2 and V3 hold carry-forward and byte-identical ledger/import evidence at the disabled switch; test candidate startup/readiness, old/new endpoint pins, same-PID readback, failure before and after activation, crash/reboot with no automatic rollback, and matching desktop MCP recovery end-to-end. Capture package hashes, SCM before/after, exact ledger/transaction hashes before new admissions, native RPC and regression results. Do not run these against Makel or the actual incident in R6.

## R7 disposable acceptance

Local Makel lacks an elevated session, Visual Studio C++ toolchain, Windows SDK and Windows Sandbox. Do not install or restart the host service to qualify this change. The opt-in `native_replacement_acceptance` input of the existing Dev Windows Installer workflow selects an independent GitHub-hosted Windows matrix, with the ordinary installer job skipped for that invocation. The script `scripts/test-windows-native-replacement-ci.ps1` refuses non-hosted/non-Windows/non-dispatch contexts and refuses an existing machine service/store or target paths. These environment checks are operator accident guards, not an attestation of a hostile environment. Run only on disposable hosted VMs, never a self-hosted runner. The workflow builds real Native Pin and NSIS packages from exact source and records hashes, but does not publish releases.

Modern mode: install the built NSIS package, create actual RPC ordinary terminal history and a V3 TerminalVerified/Prepared hold, refuse active replacement, ordinary setup/uninstall and bad candidate pin, transfer to a distinct same-source fixture binary via real SCM, verify bytes, refuse the previous endpoint pin, recover via native RPC and admit/release a new attempt. Legacy mode: compile the pinned predecessor source b331aa8, verify its native pin source matches, establish actual V2 ordinary history and terminal import hold through the installed service, transfer to the candidate, persist a boot witness and refuse same-boot release. No synthetic ledger changes are made by either hosted scenario. Modern mode is not a historical-version downgrade test. Legacy mode is not full post-reboot or MCP host-approved acceptance; those remain separate gates. The alternate binary's informational version is a fixture marker, not release version evidence. Existing normal uninstaller smoke expects successful removal of a running fresh service, which conflicts with R5's intentional quiescence/ledger gate; ordinary user uninstall/repair semantics remain a release blocker and must not be silently marked passed. The opt-in matrix does not replace normal release CI.

R7 also corrects equal install-root rejection and distinguishes ordinary shared V2 PublicationCommitted=false history from exclusive import evidence, so mixed histories do not fail solely because older ordinary entries serialized a default false fence. Actual import tombstones are still required. Hosted execution has not been run locally.

## R8 ordinary uninstall safety

Fresh service installation creates a durable empty V2 ledger only in a newly created protected machine store, with CreateNew and flushed bytes before service activation. Existing missing/ambiguous authority is not reconstructed. Production startup refuses a missing ledger. The ordinary installer no longer admits held legacy imports; the explicit forward replacement lane remains separate.

For an unmanaged V2 idle service, the authenticated administrator-only maintenance RPC atomically refuses when any ordinary RPC is in flight, checks runtime monitors and ledger state, validates the persisted store, and fences further admissions for the lifetime of that process. The uninstaller verifies the authenticated endpoint and PID with a retained process handle, disables startup, verifies again, requests graceful stop, requires stopped/PID-zero and validates the store before deleting only SCM registration. Ledger and import evidence remain. V3, held, unknown, missing, managed, or mismatched authority still refuses. No automatic rollback, cancellation of active work, or unfreeze after a lost response. A failed maintenance after the fence requires inspection; retry the maintenance request only after establishing the same intended operation and authority. Concurrent privileged maintenance is unsupported.

The hosted matrix adds an idle scenario for actual fresh installation, busy native removal refusal, terminal release, actual NSIS uninstall and retained ledger hash. Modern and legacy cases remain. Neither hosted execution nor an actual Windows reboot has been performed in local R8. A historical empty service with no persisted ledger still needs separate investigation; V3 ordinary uninstall intentionally remains unavailable to avoid unsafe historical downgrade. Source-only qualification does not establish SCM, NSIS, or signing acceptance.

## Release gates

Require exact-source CI, negative mixed-version admission tests, protected-ledger upgrade/restart tests, distinct boot and same-boot tests (simulated in isolated fixtures), original binding tests, and installed native authority/installer rollback qualification before deployment. The real legacy attempt requires fresh read-only preflight, approval to install a qualified candidate, then approval to record the witness and separately approve any actual reboot and recovery. Never force-delete runtime markers or weaken ACLs.
